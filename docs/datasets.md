# Datasets, paired evaluation, and analysis

## Versioned suites

A suite is a directory with `manifest.json` (`bus20-manifest/1`) listing every
map and scenario with its content digest, plus the files themselves:

```text
datasets/<suite>/
  manifest.json
  maps/<city>/v1/map.json
  scenarios/{dev,validation,test}/<scenarioId>.json
```

`bus20-data verify --manifest <file>` re-validates every document, checks
each digest against the manifest, and cross-checks scenarios against their
maps (stop permission, reachability). A run log names the manifest digest, so
a result can always be traced to exact inputs.

### `synthetic-dev/1`

`datasets/synthetic-dev-1/` is generated from
`datasets/configs/synthetic-dev-1.json` by `bus20-data generate`. It is a
**development suite on synthetic road networks**, not the paper's three-city
suite. Three city-like grids (irregular blocks, mixed one-way streets, per
street speeds), three loads, three demand patterns cycling within each cell,
and three splits (dev, validation, test) with three scenarios per (city, load,
split): 81 scenarios, 4 vehicles of capacity 4, 60 minutes of demand and a 90
minute completion margin.

- **Load** is a target utilisation: the fraction of fleet time that the
  requests' direct trips alone would occupy. The request count is derived
  from a map-seeded sample of direct travel times, so it adapts to each
  city's size and is identical for every scenario in a cell.
- **Patterns**: `uniform` (uniform origins, destinations, and times),
  `commute` (70% of trips from the outer zone to the centre in the first half
  of the demand window), `hotspot` (50% of trips originate in one small
  cluster during a 9-minute burst).
- Everything is seeded (`seedFromLabel(baseSeed, label)`); the generator is
  pure and the committed manifest is checked against a rebuild in tests.
  Stored request sequences are the data; the seed is provenance, not a
  substitute.

### Real cities

`tools/osm/extract_map.py` writes a `bus20-map/1` document from OpenStreetMap
through OSMnx (drivable network, largest strongly connected component, speeds
from `maxspeed` with a recorded fallback, ODbL attribution in `source`). It is
preprocessing only and is not run in CI; the maps it produces go through the
same manifest and verification path. It has not yet been executed against
live OSM data from this repository.

## Paired evaluation

```sh
node packages/runner/dist/src/cli.js suite \
  --manifest datasets/synthetic-dev-1/manifest.json \
  --policies fixture,swift --swift-cli swift/.build/release/bus20-baseline \
  --splits dev --repetitions 1 --out out/dev-baselines
```

Every policy runs on every selected scenario (paired design). Policy order
alternates per scenario so run order is not confounded with policy. Each run
is stored under `<policy>/<scenario>/rep-<k>/` with its log and result; a
finished run is reused on resume so an interrupted suite never re-spends.
`suite-index.json` is rewritten after every run and records status, pain,
failure reason, latency, tokens, cost, and replay agreement per run, with
run directories relative to the index.

## Analysis

```sh
node packages/analysis/dist/src/cli.js --suite-index out/dev-baselines/suite-index.json \
  --reference swift-insertion-reference --out out/dev-baselines/analysis
```

Writes `analysis.json` and `analysis.md`:

- **Per cell** (policy × city × load): success rate first, then mean pain
  over complete runs only, labelled as conditional, with a seeded percentile
  bootstrap 95% interval over scenarios, mean cost, latency, and failure
  reasons.
- **Paired** against the reference on identical (scenario, repetition):
  mean difference (reference minus policy), its bootstrap interval,
  improvement % with the reference as denominator (omitted when the reference
  pain is 0), policy wins, and counts of pairs where only one side completed.
  Nothing is dropped silently.
- **Across cities**: equal weight per city, so no city dominates through its
  request count.

`results/synthetic-dev-1/dev-baselines/` holds the committed index and
analysis for the fixture and Swift reference on the dev split. Run logs are
not committed; they are regenerated by the command above.
