# Bus 2.0 AI Benchmark 計画案

作成日: 2026-09-18。実装前の提案であり、以下の数値・実験規模はパイロット実験で確定する。

## 1. 目的と研究課題

実都市の道路ネットワークと固定された乗車リクエスト列を使い、AIがオンラインで配車・乗降順序を決定する能力を測る。全乗客の「待ち時間＋遠回り時間」の二乗の平均を最小化する。

Swiftの既存配車ロジックを比較基準として維持し、TypeScriptで共通シミュレーター、採点器、AI連携、実験管理を実装する。AI自身が数値を申告して採点する方式にはしない。

方式は「A: 人が書いたSwift方式」「B: AIが事前に書いたTypeScript配車プログラム」「C: 運行中の各意思決定でAIを呼ぶ方式」と定義し、研究を2本の論文に分ける。

| 論文 | 中心となる比較 | 主な問い |
| --- | --- | --- |
| 第1論文 | Cの汎用LLM対Jevを主比較とし、AのSwiftを基準に置く | 汎用LLMと判断モデルJevで、配車品質・費用・応答時間はどう違うか |
| 第2論文 | Bの初期版とSelf Improvement後の版。A・Cを比較基準として再利用 | AIが評価結果を使って配車コードを改善すると、品質・汎化・費用はどう変わるか |

当面の実装・実験範囲は第1論文とする。OpenAI、Gemini、ClaudeのモデルとJevを第1論文の評価対象に含める。具体的なモデル版と予算条件はパイロット後に固定する。A対Cだけで結論を出さず、C内の汎用LLM対Jevを中心に分析する。Bのコード生成、隔離実行、自己改善基盤は第2論文で追加し、第1論文の完成条件には含めない。共通環境には後からBを接続できるポリシー境界を設ける。

Bも新規要求ごとに現在状態を読み、動的に判断する。事前に全ルートを決める方式ではない。第2論文のSelf Improvementは開発段階で配車コードを反復改善することを指し、モデルの重み更新や本番テスト中の学習を意味しない。構造化判断専用のJevはCに参加し、公開APIにないコード生成を必要とするBは対象外とする。

研究課題は次のように設定する。

- 同じ情報・行動範囲を与えたとき、各モデルはSwift基準にどの程度近づき、または上回れるか。
- 第1論文: 同じ品質水準を満たすとき、Jevと汎用LLMの運行費用・応答時間はどれだけ違うか。Swiftに対する品質差と計算費用も測る。
- 第2論文: 評価フィードバックによるコードの反復改善は、単発生成や同予算での独立再生成より有効か。その改善は未知の需要や都市にも持続するか。
- 都市の道路形状、需要集中、負荷、運行期間が変わると性能はどう変わるか。
- ペインの低減と、API料金、推論時間、ツール呼び出し数にはどのような関係があるか。
- 失敗の原因は、制約違反、短期的な選択、需要への適応、ツール利用のどこにあるか。

論文の評価対象は、モデル単体ではなく「モデル＋固定プロンプト＋ツール＋予算＋履歴管理」の組み合わせとして明記する。

## 2. Swift版の位置づけ

既存の `Shuttle.plans` は、新規乗客の乗車・降車を既存の運行計画へ挿入する候補を列挙する。`Shuttle.bestPlan` は車両をまたいで最小の増分コストを選ぶ。既存の割当や順序を全面的に組み直す探索でも、未発生の需要を予測する探索でもない。

道路上の最短経路探索と、乗客をどの車両・順序で運ぶかの探索は区別する。「全体の最適解」「AIが到達できる性能の上限」とは呼ばず、Swift insertion baseline と位置づける。候補列挙の網羅性自体も小規模ケースで確認する。

比較基準として利用する前に、少なくとも以下を修正・検証する。

- `Evaluator` の乗車直後の区間を待ち時間にも加算する不具合。
- 移動中の車両について、現在の辺の全長ではなく残り所要時間を評価すること。
- `Graph` の並列読み取り・書き込み競合。
- 手動追加の乗客の発生時刻と、要求発生・車両到着のイベント順序。
- 無効な地図、定員、乗降順序、到達可能性の検証。

過去の実装はGitで保存し、修正前の数値を正式な基準スコアにしない。修正と意味の変更は分けて記録する。

UIKitから配車・評価ロジックを分離してSwift PackageとCLIにする。CLIは標準入出力のJSON Linesで現在状態を受け取り、行動案を返す。Swift側に独立した本番シミュレーション時計を持たせず、TypeScriptの共通環境でその行動を実行する。

## 3. 評価指標

乗客 i について、以下を定義する。

- a_i: リクエスト発生時刻。
- p_i: 実際に乗車した時刻。
- d_i: 実際に降車した時刻。
- τ_i: 同じ道路・走行時間ルールで、出発地から目的地へ直行する最短所要時間。
- W_i = p_i − a_i: 待ち時間。
- D_i = (d_i − p_i) − τ_i: 遠回り時間。
- P_i = (W_i + D_i)^2: 個人のペイン。
- P = (1/N) Σ P_i: ベンチマークの主指標。低いほど良い。

「平均を二乗」ではなく「各人の二乗を平均」する。ペインをさらに二乗することはしない。時間表示は分、Pの単位は分²に統一し、内部の整数ミリ秒から採点時に変換する。

固定走行時間では W_i + D_i = d_i − a_i − τ_i が成立する。これは、乗客が直行した場合と比べて目的地への到着がどれだけ遅れたかを表す。この等式を採点器の検証にも使う。D_iが負になった場合は、丸め誤差の許容範囲を超えれば環境の不具合として扱う。

v1は1リクエスト＝1人、乗降時間ゼロ、固定の辺所要時間とする。後続版で複数人の予約や乗降時間を追加するときは、人数による重みと直行時間の定義も版管理する。混雑を時間依存にする場合もτ_iの基準時刻を再定義し、v1の結果とは混ぜない。

副指標は平均待ち時間、平均遠回り時間、到着遅延のp95/p99・最大値、輸送完了率、車両走行時間、空車走行、時間で重み付けした占有率。AIについてはAPI所要時間、料金、トークン数、ツール回数、無効行動率も記録する。

Swiftとの比較はPの実数値を必ず示し、P_Swift > 0 のときに `100 × (P_Swift − P_AI) / P_Swift` を改善率として併記する。Swiftを上回る結果も許容し、「最適性ギャップ」とは呼ばない。

### 完了・失敗のルール

需要発生期間が終了しても、最後の乗客の降車までシミュレーションを続ける。困難な乗客を除外して平均を下げることは認めない。

- シナリオには需要終了時刻と、十分な余裕を持つ最終完了期限を固定しておく。
- 完了期限、決定回数・API予算などの上限を超えて未輸送者が残れば失敗。正式なPは +∞ とし、JSONでは `status: failed` と `pain: null` で表す。
- 全件完了した実行だけが有限の正式スコアを得る。成功率を先に報告し、成功ケースだけの平均を全体成績として提示しない。
- 全件成功していないモデルの有限値平均は補助的な条件付き統計に限定し、成功ケースの選択による偏りを明示する。
- 無効行動は状態を変更せず、固定回数まで修正機会を与える。予算超過は正式評価では失敗。基準アルゴリズムによる自動救済は別の頑健性実験とする。
- 通信障害の再試行回数と中断実験の再実行条件も固定し、成績を見て再試行を選ばない。

## 4. イベント駆動の共通環境

主時計は仮想時間。AI・Swiftの計算中は停止し、実際のAPI応答時間を乗客の待ち時間に加えない。現実の推論時間は独立に計測する。

1. 次の需要発生、走行辺の終端への到着、または予約した再判断時刻まで仮想時間を進める。
2. 同時刻のイベントを固定順で処理し、現在状態を確定する。
3. 意思決定が必要なら、同じ観測形式をポリシーに渡す。
4. ポリシーは必要に応じて読み取りツールを呼び、行動案を作る。
5. 共通バリデーターが制約を確認し、計画を原子的に反映する。
6. 次のイベントへ進み、全員の輸送完了まで繰り返す。

同時刻の処理は「辺到着 → 既定の降車 → 新規要求の公開 → 必要な意思決定 → 乗車・出発」とする。同時に現れた複数要求は全件を公開し、v1の挿入操作の対象順序はrequest IDで固定する。車両ID・辺IDによる同順位の処理順も固定する。

全交差点でAIを呼ぶ必要はない。道路上の移動は確定済み最短経路に従って自動実行し、v1では新規要求への割当時に意思決定する。拡張トラックでは車両が空いたときや明示的な再判断時刻にも呼ぶ。再判断の予約は正の時間間隔と回数制限を設け、ゼロ時間ループを防ぐ。

移動中は現在の辺を完走するまで進路変更できない。次のノード以降の計画を変更できる。再計画で残り時間を巻き戻したり、古い到着イベントを二重実行したりしない。

v1の空車は現在地に待機する。既存Swiftのランダム走行は環境ルールとしては引き継がない。これは元実装からの変更として明記する。需要の偏りを予測した空車再配置は拡張トラックの行動として比較する。

## 5. 情報と行動の公平性

### 観測

全シナリオJSONを読み込むのは実験ホストのみ。主実験ではAIにもSwiftにも未発生要求の時刻・出発地・目的地を見せない。未来の要求ファイル、生成seed、ファイル名からの検索などによる漏洩も防ぐ。評価対象モデルに自由なファイルアクセスやネットワーク検索は与えない。

観測に含めるのは、現在の仮想時刻、道路情報、車両の位置・辺の進捗・定員・乗客・運行計画、発生済み要求、過去の実行結果。同じ状態には同じ順序・粒度の観測を返す。需要の統計情報を与える実験は、その内容を全方式でそろえる。

地図全体はエピソード開始時に静的リソースとして利用可能にし、各決定で全文を再送しない。現在状態と共通経路照会ツールを使う。履歴を残す量や要約方法も実験設定に固定し、モデルごとの暗黙の補助を入れない。

### 行動トラック

| トラック | 行動 | 目的 |
| --- | --- | --- |
| v1 / Insertion | 新規要求を、選んだ車両の既存計画の乗車・降車位置に挿入。既存乗客の割当・相対順序を保持 | Swiftと同じ範囲の意思決定を比較 |
| v2 / Dispatch | 未乗車要求の再割当、将来の停車順序の組み直し、空車再配置、有限時間の待機 | より広い運行戦略を比較 |
| 補助 / Offline | 全需要を初めから公開 | 将来情報の価値と小規模問題の最適性を調べる |

乗車済み乗客の車両変更は不可、途中の乗換なし。定員、乗車前の降車禁止、要求の重複処理禁止、必須の降車の削除禁止、車両移動の連続性を共通環境が検証する。容量超過は大きなペナルティで許容するのではなく、実行不可能な行動として拒否する。

v1では候補のID・停車順・経路所要時間を共通形式で示せるが、Swiftが計算した最良候補やペイン順位をそのままAIに渡さない。候補の並び順はコストから独立させる。v2の結果とv1の結果は別表にし、行動範囲の差をモデル能力の差と解釈しない。

## 6. 地図と需要データ

サンフランシスコ、東京、ニューヨークから境界を明記した地区を選び、小・中・大のネットワークを作る。初期版は各都市の一地区に限定し、都市全域への拡張は計測後に行う。

OpenStreetMapの車両通行可能な有向道路網を候補とする。OSMnxは区域指定のネットワーク取得と、道路長・速度からの辺所要時間の作成に利用できる。[OSMnx公式資料](https://osmnx.readthedocs.io/en/stable/user-reference.html)

前処理では、一方通行、通行対象、到達可能性を検証する。歩行専用道路や車両が止まれない場所を乗降地点にしない。区域端で不自然な迂回が起きないよう、需要対象区域の外側に道路用のバッファを設ける。通行規制・右左折制約の扱いは明記し、v1で省略したものを現実の忠実な再現とは主張しない。

前処理のみPython/OSMnxを使う案とし、ベンチマーク実行系はTypeScriptとSwiftで完結する。データ取得日時、区域、元データ、加工コードの版、速度補完・丸めルール、ハッシュを固定する。実行中にオンラインの経路APIへ問い合わせない。

OSMデータはODbLで提供されるため、配布データの出典・帰属表示とライセンス情報を保存する。既存コードのCC BY-NC-SA 4.0とデータの条件を別々に記録する。[OSM公式ライセンス情報](https://www.openstreetmap.org/copyright)

### ファイル構成案

```text
datasets/
  maps/{city}/{version}/map.json
  scenarios/{split}/{scenarioId}.json
  manifests/{benchmarkVersion}.json
```

`map.json` は `schemaVersion`、`nodes`（ID・緯度経度・乗降可否）、`edges`（ID・from・to・lengthMeters・travelTimeMs・形状）、出典メタデータを持つ。

`scenario.json` は地図ハッシュ、開始・需要終了・最終完了時刻、初期車両位置・定員、全要求を持つ。要求の形式は例えば次のとおり。

```json
{
  "id": "r0001",
  "requestTimeMs": 120000,
  "originNodeId": "n101",
  "destinationNodeId": "n580",
  "passengers": 1
}
```

需要は前処理時に生成し、実行時に追加の乱数で変更しない。seedだけでなく完成した要求列を保存する。空間上一様な需要、通勤方向の偏り、局所的な集中・急増を用意し、低・中・高の負荷で評価する。都市間では単なる要求数だけでなく、直行所要時間と車両供給量も考慮して負荷を設定する。

最初の三都市共通スイートは「実道路＋合成需要」と明記する。NYC TLCの公開記録を使う拡張も可能だが、通常のタクシー記録の乗車時刻はリクエスト発生時刻ではなく、ゾーンからノードへの割当も合成になる。この仮定を保存し、実需要の完全再現とは扱わない。[TLCデータ](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page)、[Yellow Taxiデータ辞書](https://www.nyc.gov/assets/tlc/downloads/pdf/data_dictionary_trip_records_yellow.pdf)

## 7. TypeScript構成とモデル接続

```text
packages/
  contracts/       JSON Schema、観測・行動・ログの型
  simulator/       仮想時計、イベントキュー、状態遷移、制約検証
  routing/         決定的な最短経路・所要時間照会
  scoring/         独立したログ検証と最終採点
  tools/           共通ツールの実装、MCP公開
  agents/          モデル別アダプターと共通エージェントループ
  policy-build/    第2論文で追加: コード生成・自己改善・成果物の固定
  policy-runtime/ 第2論文で追加: 生成コードの隔離実行と資源制限
  baselines/       Swift CLI接続、単純な比較方式
  runner/          実験CLI、予算、再試行、保存・再開
  analysis/        集計、信頼区間、論文用出力
  viewer/          保存ログから地図・乗客・スコアを再生
swift/
  Bus20Core/       既存ロジックから抽出したSwift Package
  Bus20Baseline/   JSON Lines CLI
```

OpenAI、Gemini、Claude、TypeSafe AIのJevはそれぞれのアダプターで接続する。各モデルは同じ `decide(observation, tools, budget)` 契約に合わせる。特定のモデル名やAPIの版は実装時に公式資料で確認し、実験時には正確なIDと設定を固定する。

MCPはツールを公開する境界として採用し、各プロバイダーに直接MCP対応を要求しない。TypeScriptのホストが、共通JSON Schemaを各モデルのfunction callingへ変換する。MCPと直接呼び出しの両方が同じハンドラーを利用する。[MCP公式Tools仕様](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

ツール案:

- `get_state`: 現在の合法的な観測を取得。
- `get_travel_times`: 地点間の最短所要時間をバッチで照会。
- `get_route`: 指定した地点間の道路経路を照会。
- `list_insertions`: v1の候補を安定した順序で取得。最良解やペインによる順位は返さない。
- `validate_action`: 提案した行動の制約違反を返す。
- `commit_action`: 現在状態のversionを指定して一回だけ決定を反映。

計画の仮想実行やペイン予測を返す `evaluate_plan` は、計算支援ありの別トラックに限定する。利用回数と計算量を記録し、主実験と混ぜない。候補生成や経路検索の計算量も、AIが利用するホスト側計算として記録する。

APIによってツール呼び出しや構造化出力の機能差がある場合は、共通の最小仕様を使う。専用の追加機能を使った結果は別設定として扱う。

### TypeSafe AI / Jev の組み込み

ユーザー指定の[JavaScript SDK資料](https://docs.typesafe.ai/sdk/javascript)で接続方法を確認済み。SDKは `@typesafe-ai/sdk`、クライアントは `TypeSafeClient`、呼び出しは `client.systemOne({ state, questions, model })`。認証は `TYPESAFE_API_KEY`、SDKの要件はNode.js 20以上。SDK導入や有料API実行はまだ行っていない。

公式のモデル名はJev。公開APIは状態と型付きの質問を受け取り、Choice（選択）、Score（段階評価）、Noul（yesの確率）の回答を返す。任意の文章・コードを生成するAPIとは異なる。[TypeSafe公式Introduction](https://docs.typesafe.ai/introduction)

JevはCの運行中判断に組み込む。共通環境が合法な配車候補を生成し、現在状態と候補の停車順序・所要時間を渡し、Choiceで候補IDを選ばせる。TypeScriptホストが選択を検証して共通の行動に変換する。MCPネイティブ対応は要求しない。関数と列挙型引数をChoice等へ変換する公式例もある。[Function calling例](https://docs.typesafe.ai/cookbooks/function_calling)

比較条件は次のように分ける。

- 共通候補選択条件: 第1論文ではAとCが同一の候補集合から選び、第2論文でBも同じ契約に接続する。Jevと他のLLMには同じ状態・候補情報を渡し、追加ツールによる情報差を持たせない。候補の最良ペインやその順位は提供しない。
- ツール利用条件: 運行中に経路照会などを繰り返す条件。Jevに実装する場合は、利用可能な関数・引数を選択肢へ写像した共通ホストを介す。公開APIで表せる範囲を検証した後に追加し、候補選択条件とは別集計にする。
- 生成プログラム条件B: コード生成に対応するLLMのみを対象とする。JevのBは未対応としてN/Aを表示し、失敗スコアにしない。別のLLMが作ったコードからJevを呼ぶ方式は実行中にAIを使うハイブリッドであり、Bとして集計しない。

公式Choice仕様の上限は255選択肢。最初の共通候補選択スイートは合法候補全体がこの上限と入力長上限に収まる規模にする。大規模ケースでは共通の階層選択・分割照会プロトコルを別途定義し、モデルごとの無断の候補削除やSwiftの最良候補による事前絞り込みはしない。候補提示方式そのものの影響も記録する。[Choice仕様](https://docs.typesafe.ai/primitives/choice)

2026-09-18の確認時点で公式掲載のモデルIDは `jev-1.13.0`。実験では `jev-latest` のような移動する別名ではなく版付きIDを固定し、応答のmodelフィールドとSDK版も保存する。入力上限は1要求64kトークン、stateと最長の質問の合計32kトークンとされているため、共通条件はこれらも満たす必要がある。[Models](https://docs.typesafe.ai/models)

選択結果に加え、返された確率分布・confidenceを保存する。ただしconfidenceを配車が最適である確率やペイン値として扱わない。主条件では低confidence時にも通常どおり選択を実行し、別モデルへの切替は追加費用とともに別のハイブリッド条件で評価する。高速・低料金・判断精度に関する優位性は事前に仮定せず、同一シナリオで測定する。

## 8. 比較方式と論文の実験設計

### 第1論文: 汎用LLM対Jev、Swiftを基準とした品質・費用・速度比較

主実験は、同じ環境でオンライン配車を行う汎用LLMとJevを直接比較する。Swiftは品質と計算費用の参照基準として併記する。Jevの費用優位は検証する仮説とし、優位が成立する負荷・規模・品質水準と、成立しない条件の両方を示す。

| 比較 | 測るもの |
| --- | --- |
| 主比較: C-Jev対C-LLM | 同じ観測と行動範囲でのペイン・成功率、および同じ品質水準を満たすために必要な費用と応答時間 |
| 参照: A対C-Jev | Swift基準に対するペイン・成功率の差、実行時間と計算費用 |
| 参照: A対C-LLM | 汎用LLMがSwift基準へどの程度近づくか、または上回るか |

主条件は共通候補選択とし、各方式に同じ候補情報を提示する。合法候補の生成・経路照会と、候補からの選択を分けて測る。Swiftの候補評価器が選ぶ結果や候補のペイン順位はCに渡さない。候補の順序を変える感度分析も行う。

LLM側は同じ候補IDから選択する構造化出力を使い、Jev側はChoiceを使う。プロバイダー固有のリクエスト形式はアダプターが吸収し、観測内容、候補集合、目的関数の説明、表示言語、決定機会をそろえる。Jevだけに追加の特徴量や少数の有利な候補を与えない。LLMの推論設定に対応がある場合は予算を変えた条件も測り、費用・時間・品質の関係を示す。自由なツール利用条件は主比較とは別に集計する。

結果はモデル別・都市別・負荷別に示し、低負荷・少候補と、高負荷・多候補・急増需要で性能差がどう変化するかを見る。選択した特定のモデルとAPI・ホスト実装についての実験なので、得られた差をモデル構造全般の因果効果だとは断定しない。

費用の測定は以下を固定する。

- API料金だけでなく、候補生成、経路検索、データ整形、通信、検証を含む実行系全体を計測する。API費用、ホストCPU時間、メモリ、実時間は内訳を分け、CPU等を金額に換算する場合は使用機材・単価・換算条件を記録する。
- 1意思決定あたりの費用・応答時間に加え、1シナリオおよび要求1,000件あたりの総費用を報告する。失敗・再試行の消費も含め、失敗して途中で止まった実行を「安い成功」とは扱わない。
- 応答時間は中央値とp95、品質はペイン・完了率・遅延の分布を示す。APIの待ち時間を仮想の乗客待ち時間へ加算しない。
- 料金表の取得日、実際のトークン使用量、キャッシュ・バッチ・割引の適用条件を保存する。通常の逐次API呼び出しを主条件とし、方式ごとに有利な課金条件を無断で混ぜない。
- 地図の前処理・経路キャッシュの準備費用と、運行ごとの費用を分ける。キャッシュ状態、並行実行数、ウォームアップ条件をそろえる。
- Aも実行系全体の費用を測る。「Jevは汎用LLMより安い」と「JevはSwiftより安い」は別の仮説であり、後者を前提にしない。

品質を無視した安さで順位を付けない。主な図は横軸に運行費用、縦軸に平均ペインを置き、成功率と不確実性を併記する。さらに「Swift比でペインが事前に定めた許容範囲内、かつ所定の成功率を満たす」という品質条件の下で最小費用を比較する。許容差・成功率の基準はパイロット後、本実験前に固定する。Swiftのペインが0のケースでは比率を使わず絶対差で評価する。品質条件を満たさない方式には、その条件での費用優位を主張しない。

予算・状態の大きさ・候補数を変えた費用と品質の曲線を出し、どの条件でJevの利用が有効かを調べる。第1論文はBの生成費用や自己改善を含めず、コード生成の成否に依存しない構成にする。

### 第2論文: BのSelf Improvement

第1論文で検証した環境・指標・A/Cの比較方式を再利用し、配車プログラムの自動改善を研究する。改善する対象はBの配車コードとそのパラメーターであり、シミュレーター、採点器、データ分割、合法行動のルールは変更できない。

```text
初期コードを生成
  → 開発用シナリオで実行
  → ペイン・制約違反・失敗例・費用をAIへ返す
  → AIがコードの変更を提案
  → 共通環境で再評価
  → 事前に決めた規則で採用または棄却
  → 予算内で反復
  → 検証セットで最終版を選択・固定
  → 未使用テストセットで最終評価
```

比較群は、B0（1回だけ生成）、B-restart（同予算で独立生成し最良候補を検証セットで選ぶ）、B-self（過去のコードと評価フィードバックを使って反復改善）、A、Cとする。単発生成との差だけでなく、同じ生成・評価予算での独立再生成との差によって、フィードバックを使う効果を調べる。集計値のみのフィードバックと、失敗軌跡付きのフィードバックの比較を追加実験候補とする。

自己改善は次のルールで行う。

- 修正に使用する開発セット、版の選択に使用する検証セット、最終テストセットを分離する。検証結果を修正ループに返す場合、その検証セットは開発データとして再分類する。
- 第1論文で既に公開・観測したテスト結果を第2論文の未使用テストとみなさない。第2論文用に新しい需要seed・シナリオを確保する。
- 独立した複数の改善キャンペーンを行い、失敗、改悪、棄却した修正もすべて保存する。最高記録の1本だけを報告しない。
- 総API料金、トークン、評価シミュレーション回数、CPU時間、実時間に予算を設ける。性能を改善回数だけでなく累積費用・評価回数に対して描く。
- 採用規則と停止規則を先に固定する。全件完了・制約遵守を品質改善の前提とし、タイムアウトや例外、過大な探索コストも評価する。
- 最終版と事前指定したチェックポイントのみを凍結後にテストする。テスト成績を次の修正やチェックポイント選択に戻さない。
- 未知の需要パターン・負荷を評価し、三都市のうち一都市を開発から外す実験も行う。開発上の改善と未知条件への汎化を分けて報告する。

論文上のSelf Improvementは「評価フィードバックによるコード改善」と定義する。汎用知能やモデル自身の重みが改善したという主張はしない。

### 共通の方式定義

| 方式 | 準備段階 | 各意思決定時 | 主な比較目的 |
| --- | --- | --- | --- |
| A / Human-Swift | 人が書いた既存ロジックを修正・固定 | Swiftプログラムが現在状態から判断 | 人による探索実装の基準 |
| B / AI-Program | AIがTypeScriptの配車プログラムを生成・開発評価し、コードを固定 | 固定プログラムが現在状態から判断。LLM呼び出しなし | AIが作ったアルゴリズムの品質と再利用性 |
| C / AI-Online | 共通プロンプト・ツール・予算を固定 | AIを呼び、ツールを使って行動を決定 | 運行中のLLM推論の性能と追加費用 |

全方式が同じ仮想時間、地図、初期車両、要求列、観測、行動トラック、バリデーター、採点器を使う。Bにも未来の要求は渡さない。BとCの共通APIは `decide(observation, tools, budget)` とし、AはCLIアダプターで同じ契約に合わせる。Bはネットワークからモデルを呼ぶことも、評価ホストの需要ファイルや採点器の内部状態を読むこともできない。

Bは制限した別プロセス／コンテナ等で実行し、CPU時間、実時間、メモリ、ツール回数に上限を設ける。Cが使うホスト側ツール計算も計測する。各方式に必要な予算の種類を明示し、Swiftの探索計算、生成プログラムの探索計算、モデル推論のコストを混同しない。開発時の自由な計算支援と、評価時の共通ツール仕様は分ける。

### 第2論文における生成プログラムの作成と固定

1. Bを生成するAIには、仕様・型・ツール仕様・開発用の例・開発用シナリオでの評価結果を渡す。主条件ではSwiftの実装や最適行動ラベルは渡さず、模倣による比較を避ける。Swiftソースを渡して改善させる条件は別実験にする。
2. 生成・修正回数、トークン・料金・時間の上限を事前に決める。生成プロンプト、コード全版、評価結果、エラーを保存する。
3. 検証用セットだけで最終コードを選ぶ。テストセットを見てコードの修正や選び直しをしない。主条件は三都市で共通のプログラム1本とし、都市別コードの生成は別条件にする。
4. コード、依存関係、実行環境、モデルID、生成設定、乱数設定をハッシュ付きで固定する。人が配車ロジックを手直しした場合は、人とAIの共同実装として別に分類する。
5. 固定プログラムを未使用のテスト需要で実行する。Cも同じ開発・検証セットでプロンプトを固定し、同じテストセットで評価する。

生成のばらつきを評価するため、Bはモデルごとに独立した生成キャンペーンを複数回行う。各キャンペーン内の候補選択ルールを固定し、キャンペーン全体の失敗や成果物間の分散も報告する。最良の1本だけを事後的に選んでモデルの代表値にはしない。固定コードの反復実行と、別コードを生成する反復は区別する。

全方式のメモリはエピソード開始時にリセットする。Bはエピソード内の履歴から内部状態を更新できるが、評価中の自己書き換えやテストエピソード間の学習は主条件では認めない。Cの履歴・メモリも同じくエピソード内に限定する。Bが乱数を使う場合はseedを実験ホストが指定して保存する。

### 第2論文における費用と結論の出し方

- Bはコード生成・開発評価の費用 `G_B` と、固定コードの1運行あたりの実行費用 `R_B` を分けて記録する。
- Cはプロンプト開発等の準備費用 `G_C` と、運行中の全API・ホスト計算の費用 `R_C` を分けて記録する。
- 同じ成果物をK運行で使うときの1運行あたり費用を `G_B/K + R_B` と `G_C/K + R_C` で示す。複数のKについて比較し、準備費用を無視して一方を有利に見せない。
- Aは実行時間・資源使用を測定し、人による開発・修正工数は把握可能な範囲で別記する。人件費とAPI料金を恣意的な換算で単一指標にしない。
- 同じモデル・同じシナリオで `P_B − P_C` を測り、Cによる改善と追加費用を併記する。片方が失敗したケースも成功率に含める。
- 「CはBより良い」という結果だけで、差のすべてが運行中推論の純粋な因果効果だとは主張しない。準備予算・表現形式・実行時予算も違うため、予算を変えた比較と開発条件を公開する。

第2論文の主要図はB0・B-restart・B-selfの改善曲線、未使用条件でのペインと成功率、開発費用を運行回数で分配した費用と品質の関係とする。A・Cも同じテストセットで比較し、BとCの比較は補助的に扱う。B-selfが勝つことを前提にせず、独立再生成で同等以上の結果が得られれば、その結果を報告する。

### 補助的な比較対象

1. 単純な基準: FCFSで、合法な追加計画の中から迎車時間が短い車両を選び末尾に追加。
2. 強い従来手法: 同じ情報制約・行動範囲に対応した探索手法。拡張Dispatchトラックではrolling-horizon最適化などを検討。
3. 極小の固定問題: 列挙や最適化ソルバーで最適解を証明し、採点と基準の妥当性を検証。

未来を知るoffline最適解は、同じ目的関数・制約で厳密に最適性が証明されたときだけ、online方式に対する下界として扱う。ソルバーが時間切れになった場合は実行可能解と証明済み下界・gapを別々に記録する。未来を知る方式と知らない方式を同条件のランキングに混ぜない。

パイロットでは三都市×三負荷の9シナリオ程度で、実行時間、API料金、決定回数、成功率を確認する。その後、例として三都市×三負荷×10シナリオ＝90の未使用テストケースへ拡大し、各条件内で需要パターンを均衡させる。各モデルの反復回数はまず3回を候補とし、分散と費用から事前に確定する。

第1論文では、例えば汎用LLM3モデルとJevの計4モデル×90ケース×3反復でCは1,080エピソードになる。Aの基準実行と補助比較も加えて予算を作る。CのAPI呼び出し数はさらに決定回数・ツール往復数を掛けた規模になるため、パイロットの実測から本実験の予算を算出する。Bの生成・自己改善費用は第1論文の予算には含めず、第2論文でキャンペーン数と反復評価数に基づく別予算を作る。計画段階では有料の大量実行はしない。

- 開発・検証・テストで要求列を分離し、テストでプロンプト調整をしない。公開後の固定セットとは別に、将来の評価用の未公開セットも版管理する。
- 同一シナリオで比較するpaired designとし、反復を独立した新シナリオと誤認しない。
- 都市・負荷ごとの平均、成功率、Swiftとの差、シナリオ単位のbootstrap信頼区間を出す。都市間の総合値は都市を等重みにし、特定都市の要求数で支配させない。
- 推論予算・ツール回数・履歴条件をそろえた比較と、料金上限をそろえた比較を分ける。異なるAPIのトークン数が同じ計算量を意味するとは仮定しない。
- モデルの実行順を入れ替え、実験期間・API版・プロンプト・temperature・seed対応の有無・reasoning設定・コンテキスト管理を記録する。
- 通常需要と急増需要、短期と長期、ツール支援の有無、匿名化した都市名・IDでの評価をアブレーション候補とする。
- 決定とツール出力を保存し、将来APIの出力が変わっても同じ軌跡とスコアを再生できるようにする。非公開の内部思考は再現性の前提にしない。

LLMによる配車・経路最適化には既存研究がある。ARS/RoutBenchはLLMによる制約対応ヒューリスティック生成を評価している。第1論文はA対Cの運行中の意思決定と費用を扱い、第2論文でBのコード生成・自己改善との関係を整理する。BはARSの再現実装とは限らず、ARSと性能比較する場合はその方式を別に実装・検証する。ARSにも動的な問題は含まれるため、「静的対動的」だけを差別化の根拠にしない。第2論文では自動アルゴリズム設計・評価フィードバックによるコード改善の関連研究を別途調査し、反復改善だけで新規性があるとは主張しない。「初のベンチマーク」という主張は関連研究調査なしに行わない。[ARS/RoutBench v3](https://arxiv.org/html/2502.15359v3)

従来の動的相乗り割当との関係も整理する。[Alonso-Moraほか、2017](https://people.csail.mit.edu/jalonsom/docs/17-alonsomora-ridesharing-pnas.pdf)。さらに[LLMとVRPの2026年のサーベイ](https://arxiv.org/abs/2607.00604)を入口に、直接競合するオンライン評価を追加調査する。
